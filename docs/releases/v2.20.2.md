# csq v2.20.2

**Release date:** 2026-10-03
**Prior release:** v2.20.1 (2026-10-01)
**Checksum / signature:** see artifact `SHA256SUMS` and `.sig` files on the GitHub Releases page.

---

## What's fixed

### macOS: no more repeated keychain password prompts

Claude Code reads each terminal's login from a macOS keychain item. csq keeps
that item current when it refreshes tokens and when you switch accounts.

- **Items are now replaced, never updated in place.** csq deletes the item and
  creates it again with the same open access, instead of updating the existing
  one. Updated items could end up readable only with your password, which
  produced the recurring "security wants to access key Claude Code-credentials"
  dialogs.
- **Background work never raises the unlock dialog.** The daemon's refresh and
  sweep work no longer triggers a keychain password prompt. If the keychain is
  locked, it waits and catches up once you unlock.

### `csq swap` and fresh launches no longer refuse on leftover logins

- **Fresh launches recover from leftovers.** A terminal folder is named after
  its process id, and process ids are reused. A new terminal could inherit a
  keychain item left behind by a dead one and refuse to start with "the
  keychain holds a login csq could not identify". csq now saves that item to
  `~/.claude/accounts/keychain-quarantine/` (owner-only access, newest 10 kept
  for at most 30 days) and replaces it. The daemon clears leftovers from closed
  terminals the same way.
- **Emptied logins are replaced.** When Claude Code's own token refresh fails,
  it can leave its login with empty tokens. csq treated that as an unknown
  account, so `csq swap` refused and the terminal stayed logged out. An emptied
  login is now recognised as holding no login and is replaced. A login with
  only one empty token is still left alone.
- **`csq swap` can wait for a password dialog.** If macOS does ask for a
  password, `csq swap` waits up to 60 seconds for you to answer instead of
  giving up after 5.
- **Desktop:** removing an account no longer blocks the window while the
  keychain responds.

### Live sessions are not mistaken for dead ones

A terminal folder whose `claude` process is still running is kept, even when
csq's own launcher process has exited.

### Codex sessions keep their own instructions

When a project already has Codex's own instructions and skills, csq preserves
them, including resource files the skills reference, instead of replacing them.

## Dependencies

Updated: `anyhow`, `async-trait`, `hyper`, `log`, `tauri-plugin-single-instance`,
`tauri-plugin-updater`, `tauri-plugin-dialog`, and, in the desktop UI,
`@tauri-apps/cli`, `@tauri-apps/plugin-dialog`, `@tauri-apps/plugin-updater`,
`@testing-library/svelte`, `@types/node`, `undici`. Each Tauri plugin's
JavaScript and Rust halves are on the same version.

## After upgrading

Nothing to do. Terminals that were refusing to swap or launch work on the next
`csq swap` or `csq run`.

## Compatibility notes

- New directory: `~/.claude/accounts/keychain-quarantine/`, created only when
  csq sets an unidentified login aside. It holds credential copies, so it is
  owner-only (directory 0700, files 0600).
- No CLI flag, IPC, or `csq doctor` schema changes. Upgrade is drop-in from
  v2.20.1.
- Artifacts are signed with the same keys shipped clients already trust.
