# csq v2.20.1

**Release date:** 2026-10-01
**Prior release:** v2.20.0 (2026-09-30)
**Checksum / signature:** see artifact `SHA256SUMS` and `.sig` files on the GitHub Releases page.

---

## What's fixed

### `csq sessions share --surface codex` now works on real Codex databases

v2.20.0 introduced merging each account's Codex conversation index (the thread
list and the names you gave threads, which `resume` reads) into one shared
index. On a real machine the merge refused every time, for three independent
reasons. The tests had used simplified stand-in databases, so none of them
showed up before release:

- **Codex's own triggers were treated as tampering.** Codex creates five
  triggers in its database that keep timestamp columns in step; the merge
  assumed Codex creates none and refused the file as "hand-modified or
  malicious". Those five are now recognised by name and exact definition.
  Any other trigger, one of those names with a different body, and any view
  are still refused.
- **Closed databases could not be read.** Codex keeps its databases in WAL
  mode, and SQLite removes the companion `-wal` and `-shm` files when Codex
  closes. The merge's read-only checks then failed with "unable to open
  database file" — exactly when the merge is meant to run, with no Codex
  session open. A closed database is now read directly; only a crash
  leftover (a `-wal` without its `-shm`, or a `-journal`) is refused, with
  the recovery step.
- **Every pair of accounts looked mismatched.** The schema check compared
  *when* each database applied its upgrades, which always differs. It now
  compares *which* upgrades were applied.

The merge is also safer:

- **All-or-nothing.** The whole merge into the shared index happens in one
  database transaction. If any check fails, the shared index is left exactly
  as it was.
- **Every table is carried**, not just the conversation list, so the links
  between a conversation and the conversations started from it are kept for
  every account. A link that points at something that no longer exists is
  cleared; anything else that does not hold together refuses the merge.
- **Checked right up to the merge.** The checks are repeated on the exact
  copies being merged, and the shared index's schema is re-checked inside the
  transaction itself, so a Codex upgrade that lands in between is refused
  rather than merged.
- **A backup first.** Before merging into an existing shared index, csq takes
  a consistent copy of it (`<name>.pre-merge-<time>-<pid>`, readable only by
  you, the three most recent kept) and names it in the output and in any
  error that leaves it in place. (A merge that is refused before anything
  is written deletes the backup, since the index was never touched.)
- **Accounts are never left empty.** If linking an account fails partway,
  csq puts the account's own file back. If that cannot be confirmed, the
  error names the account and where its file is.

Rehearsed on copies of a real four-account setup: all 7,491 conversations,
all 39 thread names and all 6,853 conversation links were kept, with no broken
links; adding two more accounts to an already-shared index gave the same
result, and re-running changed nothing.

## After upgrading

If you use Codex on more than one account, close your Codex sessions and run:

```
csq sessions share --surface codex
```

If it reports two accounts "at different codex schema versions", one account
has not been opened since you upgraded Codex. Start Codex once on the account
with fewer migrations (`csq run <slot>`, then quit) so Codex upgrades its own
database, then run the command again. csq does not upgrade Codex's database
itself.

## Compatibility notes

- No on-disk layout, CLI flag, IPC, or `csq doctor` schema changes. Upgrade is
  drop-in from v2.20.0.
- Artifacts are signed with the same keys shipped clients already trust.
